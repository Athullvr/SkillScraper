# SkillScout evaluation v1

This version defines a fixed 15-task evaluation set in [`tasks.jsonl`](tasks.jsonl): five routine tasks expected to need no skill, five tasks where specialized guidance may help, and five weak-match, incomplete-evidence, or suspicious-candidate cases. Human relevance criteria are recorded per task before any catalog-backed comparison. They are based on task requirements, not SkillScout scores or rank order.

The task set is a small, authored benchmark. None of these prompts are represented as actual developer requests. The critical-risk case is explicitly a synthetic policy fixture, not a catalog candidate. The earlier 20-task exploratory set remains at [`../tasks.jsonl`](../tasks.jsonl) and is not silently replaced by this version.

## Judgment and comparison protocol

For each ordinary skills.sh search result and each SkillScout candidate, inspect the detail record and label task relevance against that task's `human_relevance_judgment.criteria`. A name, description, install count, search snippet, SkillScout score, or rank alone is not evidence of relevance. Record the real stable ID and detail content hash only after receiving them. If content is unavailable or cannot be tied to a returned identity, label relevance `unknown`, not relevant or irrelevant. Keep compatibility separate from task relevance.

Use a paired comparison for each of the 14 live-catalog tasks:

1. Run ordinary catalog search with the exact task text and record the first three stable IDs in returned order, request time, response status, and elapsed time.
2. Run SkillScout for the same task and project context with the optional LLM disabled. Record its decision, first three candidate IDs, compatibility, evidence states, content hashes, audit revision associations, warnings, and elapsed time.
3. Fetch and inspect candidate details through the documented API. Under the proposed v1.1 review procedure, two reviewers independently apply the predeclared criteria using packets containing the task, unchanged criterion, approved project context, and candidate detail. The packet hides arm/system, rank, SkillScout score/decision, popularity, audit, and scanner findings; the reviewer crosswalk is inaccessible. Reviewers record source recognition. Content-based source recognition alone does not invalidate a label, but must be disclosed as a blinding limitation. If protected metadata is exposed, record what was exposed, to whom, and when; preserve the assessment, mark it compromised, and obtain an unexposed replacement assessment if available. If no replacement is available, report the affected judgment as unresolved rather than fully blinded. A third reviewer first records and locks an independent blinded label/reason, then sees the two locked initial labels/reasons and records adjudication without seeing system, rank, or crosswalk. Never install or execute a candidate.
4. Keep search and SkillScout measurements paired to a catalog time window. Repeat the pair three times and record observed IDs/hashes because the catalog can change between requests. Preserve raw API response metadata only as needed for reproducibility; do not check in skill documents, credentials, or project source.
5. Run the synthetic critical-risk case only against the deterministic local policy fixture. It is not part of live search precision/recall or host results.

The 14 live tasks are the ten routine/useful tasks plus four weak or incomplete-evidence tasks. The synthetic case is excluded from catalog queries. For the routine and weak-match tasks, an irrelevant returned candidate is an unnecessary recommendation. For useful tasks, count a useful selection only when the inspected content meets the human criteria. A relevant skill absent from the top three is a miss only when the relevant content and identity could actually be established. Report unresolved candidates as unknown.

## Measures

- **Useful-skill selection:** relevant inspected candidates among the top three, reported for each system and task.
- **Unnecessary recommendations:** irrelevant candidate slots among the top three for the five expected no-skill tasks and two weak-match tasks. Empty slots are not recommendations.
- **Relevant skills missed:** predeclared task concepts not represented by an inspected relevant candidate in the top three. Unknown mappings are reported separately.
- **Decision outcomes:** counts of `NO_SKILL_NEEDED`, `USE`, `REVIEW`, and `AVOID`, judged against the per-task expected behavior. Ordinary search has no policy decision and is not credited for these categories.
- **Evidence completeness and provenance:** stable identity/source, inspected detail completeness, content hash, audit availability/freshness/revision match, compatibility status, and scanner findings. A hash identifies returned content; it does not authenticate its publisher. A clean heuristic scan is not proof of safety.
- **Time to useful decision:** wall-clock time from request start through a result that a human can judge, measured separately for ordinary search and SkillScout. Record errors and incomplete results as failures with time, not as fast decisions.

Report task-level values and aggregate counts; do not infer general accuracy or statistical significance from 15 tasks. The security fixture is simulated. Fixture-based unit tests are offline. A live API run requires authorized credentials. Actual developer-task performance is not measured by this dataset.

## Reproduction and authentication

Pin the SkillScout checkout/revision, Python version, catalog date, project context, candidate limit, and whether the optional LLM is disabled. Run `skillscout doctor` first. For SkillScout's normal recommendation, use the same task text and project context for each task; the MCP `prepare_task` path always disables the optional LLM. For ordinary search, use the documented `GET /api/v1/skills/search?q=...&limit=...` API and preserve the first three IDs.

The current [skills.sh API reference](https://www.skills.sh/docs/api) documents Vercel OIDC bearer authentication and says the audit endpoint requires authentication. Local setup requires a linked Vercel project and a fresh `VERCEL_OIDC_TOKEN` made available to the SkillScout/search process. SkillScout reads `VERCEL_OIDC_TOKEN` or the `SKILLSCOUT_CATALOG_TOKEN` bearer-token override from its process environment; it does not load `.env.local` or refresh tokens. Never include token values in commands saved to history, result files, MCP configuration, or chat. The docs do not describe an unauthenticated search/detail route or a separate skills.sh API key. See [Vercel OIDC](https://vercel.com/docs/oidc) for the supported local setup.

## Harness readiness audit

The preregistered 15-task dataset, criteria, expected outcomes, metrics, and exclusions remain unchanged: 14 tasks are in the live-catalog cohort, and the synthetic critical-risk task remains excluded. The task IDs and fixture checklist are in the dated addendum. The addendum is a proposal pending explicit human approval.

The proposed primary comparison is end-to-end: ordinary search returns the catalog's first three results, while SkillScout uses its existing retrieval and ranking pipeline. With candidate limit three, the current SkillScout implementation searches a pool of 18 before returning up to three ranked candidates. This comparison does not isolate ranking quality. The baseline makes one request without automatic retries; errors remain failures.

The proposed addendum uses a fixed schedule of 21 ordinary-first and 21 SkillScout-first pairs. Per-repetition counts are 6/8, 8/6, and 7/7 (ordinary-first / SkillScout-first); category totals are routine 7/8, helpful 8/7, and weak or incomplete-evidence 6/6. It does not balance every repetition/category cell and is not randomized. Execution is repetition-major: all eligible tasks in dataset order for repetition 1, then repetition 2, then repetition 3, preserving each pair's assigned arm order. The five-minute pairing window is measured between arm invocation start times; timestamps limit elapsed time only, and the catalog provides no shared snapshot guarantee.

The addendum proposes an unapproved 240-second wall-clock cap for each arm invocation, followed by immediate invocation of the second arm in assigned order. The four-minute proposal leaves up to one minute within the five-minute start window to dispatch the second arm if the first reaches its cap; it is not based on a measured service guarantee and may time out SkillScout's existing multi-request/retry workflow. No runner currently enforces this cap. Its enforcement and ability to proceed after the caller stops waiting remain unverified; a timed-out underlying call may continue and overlap the second arm. At the cap, record the arm as failed with `invocation_timeout`, a null SkillScout decision if no valid response arrived, and no fabricated result; classify the pair as failed if neither arm has a valid primary response, otherwise partial when an arm fails/times out. A timeout is an operational failure, not a useful decision. The ten-minute post-arm lookup budget begins when the later invocation returns, errors, or reaches the proposed harness timeout.

The proposed post-arm detail/audit phase has one shared ten-minute budget per pair, starting when the later arm invocation returns, errors, or reaches the proposed invocation cap. Evaluation-only detail/audit requests use one attempt and no retries, in invocation order, candidate rank order, and detail before audit. Late results are supplemental and excluded from primary review; missing, failed, unlinked, or mismatched evidence remains unknown. SkillScout's normal product retry behavior is preserved and may be asymmetric with these evaluation-only lookups. Hard cancellation is not verified: the underlying HTTP request/connection must be shown to terminate before cancellation can be claimed. If useful detail is unavailable by the cutoff, Time to useful decision is censored/incomplete, not a successful decision at ten minutes. The addendum also specifies arm/pair statuses, nullable decisions, evidence-linkage fields, the reviewer crosswalk, and the two-reviewer/third-reviewer adjudication process.

All 14 task contexts remain blocked. The proposed fixture paths are not created or pinned; review the task-by-task checklist and resolve its open context facts before approving or running a task. The addendum proposes two independent reviewers and third-reviewer adjudication, but reviewer availability has not been confirmed.

No recorder or validator is implemented, and no live rows have been collected. The addendum does not authorize fixture creation, recorder implementation, catalog requests, or data collection. Reviewer availability and authorized catalog access remain unconfirmed. Recorder implementation and live collection each require separate approval after the protocol and task contexts are approved.

The dated [v1.1 protocol addendum](addendum-2026-10-20.md) contains the proposed operational choices and fixture approval checklist. It remains pending approval and does not authorize data collection.
