# SkillScout evaluation v1

This version defines a fixed 15-task evaluation set in [`tasks.jsonl`](tasks.jsonl): five routine tasks expected to need no skill, five tasks where specialized guidance may help, and five weak-match, incomplete-evidence, or suspicious-candidate cases. Human relevance criteria are recorded per task before any catalog-backed comparison. They are based on task requirements, not SkillScout scores or rank order.

The task set is a small, authored benchmark. None of these prompts are represented as actual developer requests. The critical-risk case is explicitly a synthetic policy fixture, not a catalog candidate. The earlier 20-task exploratory set remains at [`../tasks.jsonl`](../tasks.jsonl) and is not silently replaced by this version.

## Offline implementation status

The authorized engineering milestone created content-addressed contexts for all 14 eligible tasks and an evaluator-only `contexts/fixtures.lock.json`. Each task directory has a canonical `MANIFEST.sha256`; the lock is pinned to the unchanged dataset hash. Ten contexts are marked ready for protocol-owner review. Four remain `incomplete_by_protocol` because task facts were not provided: the existing test framework, the established test command/framework, the PostgreSQL column and quantitative workload, and the Terraform starting policy/trust relationship. Their slots remain in the fixed schedule but are blocked until those facts are resolved. The fixture lock has no Git commit recorded because this milestone does not permit commits.

The offline recorder, restricted run store, blinded-review packet/ledger, metric derivation, validator, and a process-isolated runtime adapter are implemented under `src/skillscout/evaluation/`; `python -m skillscout.evaluation` provides fixture pin/verify, run validation, and metric commands. The adapter connects the existing SkillScout MCP operation, ordinary search, and detail/audit lookup operations to the recorder interfaces, but it is not enabled by the offline CLI and does not enable live run persistence. Offline tests exercise monotonic deadline handling with local fake workers. A timed-out worker is terminated locally when possible, while termination of an upstream request remains `not_confirmed`; the adapter quarantines itself and the recorder stops further invocations. No live catalog request or remote cancellation test has occurred.

No catalog request, credential access, reviewer session, or evaluation data collection occurred during implementation. Live evaluation remains separately unauthorized.

## Judgment and comparison protocol

For each ordinary skills.sh search result and each SkillScout candidate, inspect the detail record and label candidate relevance against the unchanged task criterion. Candidate relevance (`relevant`, `irrelevant`, or `unknown`) is separate from the task-level expected label/decision in `tasks.jsonl`. A name, description, install count, search snippet, SkillScout score, or rank alone is not evidence of relevance. If content is unavailable or cannot be tied to a returned identity, candidate relevance is `unknown`, not relevant or irrelevant. Keep compatibility separate from task relevance.

Use a paired comparison for each of the 14 live-catalog tasks:

1. Run ordinary catalog search with the exact task text and record the first three results in returned order, request time, response status, and elapsed time.
2. Run SkillScout with the same exact task text and its separately approved project context, with the optional LLM disabled. Record its decision, first three candidate IDs, compatibility, evidence states, content hashes, audit revision associations, warnings, and elapsed time.
3. Fetch and inspect candidate details through the documented API. The blinded-review workflow is implemented for offline packet construction and append-only review records; reviewer assignment and approval remain prerequisites for collection. Two reviewers independently apply the predeclared criteria using blinded packets. The packet hides arm/system, task-level expected labels/categories, rank, score, popularity, safety findings, and reviewer crosswalk; stable candidate IDs and source URLs are masked where feasible. Reviewers record source recognition and any unavoidable metadata exposure. If protected metadata is exposed, preserve the assessment, mark blinding compromised, and obtain an unexposed replacement if available; otherwise mark the review unresolved. Candidate relevance labels are separate from task-level judgments. A third reviewer first locks an independent blinded label/reason, then sees the two locked initial reviews and records adjudication. Never install or execute a candidate.
4. Keep search and SkillScout measurements paired to a catalog time window. Repeat the pair three times and record observed IDs/hashes because the catalog can change between requests. Preserve raw API response metadata only as needed for reproducibility; do not check in skill documents, credentials, or project source.
5. Run the synthetic critical-risk case only against the deterministic local policy fixture. It is not part of live search precision/recall or host results.

The 14 live tasks are the ten routine/useful tasks plus four weak or incomplete-evidence tasks. The synthetic case is excluded from catalog queries. For the routine and weak-match tasks, an irrelevant returned candidate is an unnecessary recommendation. For useful tasks, count a useful selection only when the inspected content meets the human criteria. A relevant skill absent from the top three is a miss only when the relevant content and identity could actually be established. Report candidates with insufficient evidence as unknown; report unresolved reviewer adjudication separately.

### System-facing input boundary

For each of the 14 eligible task rows and each of its three repetitions, the ordinary-search arm receives only the exact `task` string as its query, without project context, filters, evaluator notes, or a rewritten prompt. SkillScout receives that same exact `task` string plus only the separately approved, pinned context fixture for that task; it does not receive the raw evaluator record. The fixture is the sole project-context input to SkillScout. Apply this rule per task ID without exposing the ID itself.

Neither arm receives evaluator-only `id`, `category`, `expected_decision`, `human_relevance_judgment`, measurement fields, `measurement_scope`, `fixture_description`, reviewer labels, expected-answer notes, or this protocol's fixture descriptions. The `project_context` field is not passed verbatim. In particular, for `review-stripe-webhook-audit`, withhold the phrase “current inspected revision has no verified revision-bound external audit evidence” and any equivalent direct or indirect disclosure of the expected audit state or outcome. The approved fixture and its description must not seed or imply audit state, candidate identity, candidate relevance, or the expected decision. These exclusions preserve the existing dataset and its hash.

Arm outputs are bounded too: ordinary search contributes only its first three returned results in response order; SkillScout contributes its primary decision and up to its first three recommendations in SkillScout order, plus fields actually returned by that arm. The evaluator stores pairing, status, evidence-lookup, and judgment metadata separately. Candidate-relevance reviewer packets contain the candidate detail evidence needed to assess relevance, together with the task text, unchanged relevance criterion, and an approved context description scrubbed of expected-outcome disclosures. They exclude system or arm identity, system decisions, ranks and other rankings, scores, popularity, protected safety/audit and scanner findings, task-level expected labels/categories/decisions, and the reviewer crosswalk. For the Stripe task, packets also exclude the quoted evaluator-only audit-state phrase and equivalent direct or indirect audit-state/outcome disclosures. A separate task-level decision-conformity review is described in the addendum; it retains these exclusions and does not show reviewers the original decision.

## Measures

### Primary estimand

The primary metric is **confirmed relevant-slot yield@3 per planned slot**. It is the end-to-end yield over the three planned top-three positions for each arm and repetition; it is not relevance among successfully inspected candidates.

For task `i` (14 eligible tasks), arm `a` (`SkillScout` or `ordinary search`), and repetition `r` (three per task), let `R_iar` be the number from 0 to 3 of planned slots occupied by a candidate in a valid primary response, with complete identity-linked detail sufficient to apply the task's relevance criterion available by the shared 600-second deadline, and a final resolved candidate label of `relevant`. Late responses or evidence are supplemental and do not count. For each repetition, calculate `q_iar = R_iar / 3` and `d_ir = q_i,SkillScout,r - q_i,ordinary,r`. Average the three repetition differences within each task, then average the 14 task means equally: `D_i = (d_i1 + d_i2 + d_i3) / 3`; `Delta = sum(D_i, i=1..14) / 14`. The primary contrast is `Delta`, SkillScout minus ordinary search. Its fixed denominator is three planned slots per arm per repetition: 126 slots per arm across the cohort.

A failed, blocked, or uninvoked arm has `R_iar = 0`; this means it produced no confirmed relevant slots, not that any candidate was irrelevant. Empty, unknown, unresolved-review, failed, blocked, not-run, and absent/truncated slots add no numerator and retain their separate status. A parseable partial response may contribute only occupied slots that individually meet the primary-response, timely-detail, and final-label requirements; missing positions remain unknown. Do not delete incomplete pairs from the primary calculation.

For the predeclared complete-pair sensitivity analysis, a repetition is eligible only if both arms were invoked, each returned a valid complete primary response within the 240-second cap, the second invocation started within the inclusive 300-second window, and every occupied candidate slot has complete, identity-linked detail sufficient to apply the task relevance criterion by the shared 600-second deadline. A valid complete empty response satisfies the evidence condition without candidate detail. Determine eligibility from invocation, response, timing, and evidence-completeness/linkage fields before relevance labels or comparative results are considered; unknown or unresolved labels do not change eligibility. Use the same fixed three-slot denominator for eligible repetitions. Within each task, average eligible repetition differences; then give equal weight to each task with at least one eligible repetition. Report each task's eligible repetition count, the number of contributing tasks, and tasks with none. This sensitivity analysis does not replace the primary estimate.

### Secondary metrics

- **Evaluable-slot precision:** `relevant / (relevant + irrelevant)` among occupied slots with final resolved labels. Unknown and unresolved-review labels are excluded from this denominator and reported separately; always show the numerator and denominator.
- **Top-three coverage:** for each arm, task, and repetition, report whether at least one of the three planned slots is confirmed relevant. Claim no relevant candidate only when the response is complete and every occupied candidate is assessable; otherwise report indeterminate. Use 42 planned task/repetition opportunities per arm and keep empty, unknown, and failed states distinct.
- **Conditional task-level decision conformity:** score SkillScout only, and only when its primary response contains a valid non-null `NO_SKILL_NEEDED`, `USE`, `REVIEW`, or `AVOID` decision. An independent decision-conformity review classifies an assessable decision as `CORRECT` or `INCORRECT`; inadequate evidence, unresolved review, or no valid decision is `INDETERMINATE`. A valid decision in a parseable partial response may be assessed only if the decision-relevant evidence is sufficient; retain its partial status. Report null, failed, blocked, and uninvoked outcomes separately. Do not combine this measure with candidate relevance or assign a policy decision to ordinary search. Task categories, expected decisions, task-level judgments, and the original system decision remain hidden from reviewers during independent assessment. Because the synthetic critical-risk task is excluded from the live cohort, this study cannot establish `AVOID` reliability. The addendum defines the evidence gates and remaining decisions.
- **Operational outcomes:** report arm status counts per 42 planned arm opportunities for each system and pair status counts per 42 planned pairs. Show failure, timeout, partial, blocked, and `not_run` separately; report timeout rates both per invoked arm and per planned arm opportunity. Report evidence availability among occupied slots from valid primary responses, with missing, late, failed, unlinked, mismatched, and unknown states separately.

- **Unnecessary recommendations:** irrelevant candidate slots among the top three for the five expected no-skill tasks and two weak-match tasks. Empty slots are not recommendations.
- **Relevant skills missed:** predeclared task concepts not represented by an inspected relevant candidate in the top three. Unknown mappings are reported separately.
- **Evidence completeness and provenance:** stable identity/source, inspected detail completeness, content hash, audit availability/freshness/revision match, compatibility status, and scanner findings. A hash identifies returned content; it does not authenticate its publisher. A clean heuristic scan is not proof of safety.
- **Time to useful decision (TUD):** define `evidence_ready` for relevance as the later of (a) receipt of a complete primary arm response and (b) availability, for every occupied candidate slot, of complete detail whose identity is linked to the returned candidate and whose content is sufficient to apply the unchanged relevance criterion. A valid empty search or `NO_SKILL_NEEDED` response with no candidates is evidence-ready when that response arrives. Per-arm TUD is the monotonic duration from that arm's invocation start to its `evidence_ready` event. A partial primary response may contain individually assessable candidates, but arm-level `evidence_ready` and TUD remain incomplete because the primary result is incomplete and absent/truncated positions remain unknown. If required relevance evidence is missing, failed, late, unlinked, mismatched, or otherwise insufficient at the shared lookup deadline, TUD is censored/incomplete; the cutoff is never a successful decision time. A timeout or harness failure is also failed/incomplete, never success. TUD can include time waiting for the paired arm before shared lookups begin; it is a protocol-workflow measure, not isolated system latency.
- **Relevance versus safety evidence:** candidate relevance may be assessable when its linked detail is sufficient to apply the task criterion even if its safety/audit status remains `unknown` or `unverified`. Safety/audit evidence is tracked separately and is not required for relevance `evidence_ready`; its absence never implies safety or establishes a safety-dependent policy decision as correct.
- **Timing components:** report arm response latency, evidence-retrieval duration, time waiting for the paired arm to reach its terminal primary state, and pair-level time to evidence-ready separately. Pair-level time to evidence-ready runs from the first invocation start until both arms have reached relevance `evidence_ready`; report it as not assessable if an arm was never invoked and incomplete/censored if either arm lacks a complete primary response or required relevance evidence is not ready by the cutoff. Do not substitute one component for another.
- **Slot outcomes:** for each arm, report relevant, irrelevant, unknown, unresolved-review, empty, failed, blocked, and not-run outcomes separately. The fixed-slot denominator is 126 planned top-three slots per arm (14 tasks × 3 repetitions × 3 slots). Also report an evaluable-occupied-slot denominator consisting only of occupied slots with a final relevant/irrelevant label; show unknown and unresolved-review occupied slots separately. Failed, blocked, not-run, empty, unknown, and unresolved-review slots never count as irrelevant.

The planned 42 pairs are repeated observations clustered within 14 tasks, not 42 independent tasks. The estimand weights the 14 eligible tasks equally after averaging within each task; it describes this authored cohort. Treat the task as the interpretation unit; report pair/repetition and arm-order effects descriptively. Do not infer general accuracy or statistical significance from this small set. The security fixture is simulated. Fixture-based unit tests are offline. A live API run requires authorized credentials. Actual developer-task performance is not measured by this dataset.

### Decision conformity (secondary; SkillScout only)

Candidate relevance asks whether a candidate's inspected content addresses the task criterion. Decision conformity asks whether the task-level action is justified; the outcomes and denominators are separate. A relevant candidate does not by itself justify `USE`: identity-linked content, material task fit, compatibility/integration requirements, and any applicable safety/audit gate must also be established. Conversely, an optional relevant candidate does not by itself make `NO_SKILL_NEEDED` incorrect when the task is self-contained and the candidate adds no material task-specific value. The materiality threshold remains for human approval.

The approved rubric treats `NO_SKILL_NEEDED` as justified only when task requirements and approved context support that no skill is needed, or adequate candidate assessment finds no candidate with material task-specific value; an empty or failed search alone is not proof. `USE` requires an identified, relevant candidate, adequate compatibility/integration evidence, and every applicable required safety/audit gate to pass. `REVIEW` requires a plausible relevant candidate plus a specific decision-critical uncertainty or conflict that could change the action; an evaluator-only lookup failure does not show that SkillScout knew of the uncertainty. `AVOID` requires affirmative, current, candidate- and revision-linked evidence of a critical or prohibited risk; missing, stale, mismatched, or unavailable audit evidence is not evidence of danger. Exact task-level thresholds and precedence remain open as listed in the addendum.

Decision-time evidence is the task and approved context plus information actually available to SkillScout before its decision. Retrospective evaluator evidence may verify candidate content or a revision within the existing evidence deadline, but cannot be attributed to SkillScout as knowledge. Evidence arriving after the 600-second deadline is supplemental and cannot change the primary conformity assessment. Reviewers must have enough evidence to justify an action without seeing system identity, original decision, expected task labels/categories, scores, ranks, popularity, the reviewer crosswalk, or protected audit-state disclosures. If required evidence cannot be included without violating the existing protection for the Stripe audit-state phrase or protected findings, mark conformity `INDETERMINATE` pending an approved blinded evidence procedure.

`CORRECT` and `INCORRECT` require sufficient task/context and decision-relevant evidence, a valid decision, and a resolved independent review. `CORRECT` means the decision matches the independently justified action; `INCORRECT` means sufficient evidence supports a different action. Use `INDETERMINATE` when required evidence is missing, late, stale, mismatched, insufficient, or unresolved; when the decision is null/invalid; or when the arm failed, was blocked, or was not run. Operational failure is still reported separately, and a failed or uninvoked arm is never silently converted to `NO_SKILL_NEEDED` or `REVIEW`.

Two reviewers assess each decision independently from identity-masked evidence without seeing the original decision; preserve and lock both initial assessments before adjudication. A third reviewer first locks an independent assessment, then reviews the initial locked assessments. Preserve all rationales. If disagreement remains unresolved, or blinding is compromised without an unexposed replacement, report `INDETERMINATE`. Score repetitions individually, report `CORRECT`/`INCORRECT`/`INDETERMINATE` counts for each of the 14 tasks, and treat tasks as interpretation units. Any descriptive task-macro correct rate averages each task's `CORRECT / (CORRECT + INCORRECT)` over assessable repetitions, then averages across tasks with at least one assessable repetition; always report the contributing-task count and indeterminate observations. This secondary summary does not alter the fixed primary estimand.

## Reproduction and authentication

Pin the SkillScout checkout/revision, Python version, catalog date, approved per-task context, candidate limit, and optional-LLM state. Run `skillscout doctor` first. For SkillScout's normal recommendation, use the exact task text and the approved task context; the MCP `prepare_task` path disables the optional LLM. For ordinary search, use the documented `GET /api/v1/skills/search?q=...&limit=3` API with the exact task text only, no project context, and preserve the first three results in returned order.

The current [skills.sh API reference](https://www.skills.sh/docs/api) documents Vercel OIDC bearer authentication and says the audit endpoint requires authentication. Local setup requires a linked Vercel project and a fresh `VERCEL_OIDC_TOKEN` made available to the SkillScout/search process. SkillScout reads `VERCEL_OIDC_TOKEN` or the `SKILLSCOUT_CATALOG_TOKEN` bearer-token override from its process environment; it does not load `.env.local` or refresh tokens. Never include token values in commands saved to history, result files, MCP configuration, or chat. The docs do not describe an unauthenticated search/detail route or a separate skills.sh API key. See [Vercel OIDC](https://vercel.com/docs/oidc) for the supported local setup.

The primary comparison is defined as end-to-end, not a ranking-quality test. Ordinary search receives the task text without project context, makes one request with `limit=3`, and returns its first three results in catalog order. SkillScout receives the exact task text plus approved context, searches a larger pool, ranks and inspects candidates, and retains its existing retry behavior. With candidate limit three, the current implementation is documented as searching a pool of 18 before returning up to three; this and the retry behavior are not runtime-verified by this protocol. Differences may reflect context, search-pool size, ranking, policy, inspection, or retries.

Execution is repetition-major in dataset order. Pairing uses monotonic elapsed time from the first invocation-start event to the second; the second must start at or before 300 seconds. If the deadline passes before the second arm starts, do not launch it: mark that arm `not_run`, the pair `partial`, and leave its start timestamp absent. UTC timestamps are recorded for auditability. The catalog provides no shared snapshot guarantee.

The approved protocol sets a 240-second per-invocation cap. The adapter enforces a monotonic process deadline, including worker launch time, and terminates the local worker process group on timeout; an isolated one-second timeout test verifies local worker cleanup, not remote request cancellation. A harness timeout is a failed/incomplete arm, never a decision and never proof that the underlying request was cancelled. Record harness timeout separately from underlying-request termination (`confirmed`, `not_confirmed`, or `unknown`). If any invoked operation reports termination as `not_confirmed` or `unknown`, stop further invocations pending human review, even if a response was returned; do not claim cancellation. A late response is supplemental only. Pair status and the 300-second boundary are defined in the addendum. The shared 600-second lookup budget begins only after both invoked arms reach terminal primary states; no pair-level lookups run if either arm was never invoked. The adapter passes and checks the remaining monotonic lookup deadline. The live catalog configuration and remote cancellation behavior remain unverified.

The addendum specifies a shared 600-second post-arm detail/audit budget, lookup order, and late/unknown handling. The approved order follows assigned arm order, candidate rank ascending, and detail before audit; this gives earlier arms and higher-ranked candidates priority if the budget expires. The timing components, slot denominators, task clustering, blinded labels, and reviewer-exposure rules are specified in the addendum. This documentation does not establish software enforcement.
