Each `MANIFEST.sha256` is generated from fixture files only and excludes itself:

1. Include every regular file beneath that task's fixture directory except the root-level MANIFEST.sha256 itself. Reject symlinks and non-regular files; do not silently omit hidden files.

5. Encode the manifest as UTF-8. Record its SHA-256 and the Git commit containing the fixture pack. Do not include the manifest in its own input file set.

### Approved arm invocation cap policy; runtime enforcement unverified

Retain a maximum wall-clock duration of **240 seconds per arm invocation**, measured from the invocation-start event until a valid response or terminal error. If the first arm reaches the cap and termination is confirmed, the remaining 60 seconds in the 300-second pairing interval are only a nominal dispatch margin for starting the second arm; dispatch delay consumes that margin. The process-isolated adapter applies a monotonic deadline starting before worker launch and kills the local worker process group at expiry. An offline one-second worker test verifies local cleanup; it does not measure a live 240-second request or prove upstream cancellation. Because `Popen` process creation is synchronous, an operating-system stall inside process creation itself is not preemptible by the adapter. The policy is not a measured service guarantee and may time out SkillScout's multi-request/retry workflow. Before collection, review the pinned runner and verify the live configuration and recorded outcomes.

Record harness outcome separately from underlying-request termination. Use `confirmed`, `not_confirmed`, or `unknown` for termination status, with supporting evidence; a harness stopping its wait is not proof that the process, MCP call, transport, or HTTP request stopped. A harness timeout is not proof of cancellation. Do not claim cancellation without positive evidence that the underlying request terminated. A cap expiration is `failed`/incomplete with `invocation_timeout`, no valid primary result, and a null SkillScout decision if no valid decision was received. It is never a successful decision. Preserve a response received after the cap only as supplemental late evidence; it does not revise the primary status or decision.

Invoke arms sequentially in assigned order. If any invoked operation reports underlying termination as `not_confirmed` or `unknown`, stop further arm invocations pending human review, even if it returned a valid response; do not claim cancellation or start another invocation while termination is unresolved. This includes timeouts and unexpected harness failures. Record any unstarted scheduled arm as `not_run`, without a fabricated start time, and the pair as `partial`. Resume only after review resolves whether continuation is safe, and only if the pairing deadline has not passed. If termination is confirmed, the second arm may be attempted only if it can start at or before 300 seconds. Once that deadline has passed, do not launch the arm; mark it `not_run` and the pair `partial`. A late response remains supplemental and does not restart a stopped run automatically.

This stop-for-review rule halts subsequent arm invocations. If both arms have already been invoked and reached terminal primary states, apply the shared pair-level lookup budget below; if either arm was never invoked, run no pair-level lookups.

For an unexpected harness failure, record `harness_failure`, the last verified event/time, and any observed underlying-request termination status. Keep any valid response already received as that arm's primary response; for an invocation without a valid response, record `failed` and a null decision, never a fabricated value. If the harness failed before an invocation started, mark that arm `not_run` and leave its start time absent. If termination is `not_confirmed` or `unknown`, stop all further invocations pending human review.

A timeout, harness failure without a valid response, or missing result never becomes `NO_SKILL_NEEDED`, an empty successful search, or a successful TUD observation. Pair classification is defined in Section 4.

The five-minute window limits elapsed time between arm invocation starts; it does not create a shared catalog snapshot. Record catalog-provided Date, ETag, and request identifiers when actually returned, plus stable IDs, observed revisions/hashes, audit timestamps, and each detail/audit retrieval time. No snapshot consistency may be claimed solely from timestamps or matching identities.

For each returned candidate, record:
- The exact stable ID (source/slug), arm, and rank.
- Detail identity, detail retrieval status, content hash, revision if exposed, and retrieval time.
- Whether the detail can be tied to the search/tool observation: identity_linkage is matched only when the stable ID exactly matches; otherwise it is unverified. If the arm exposed a content hash/revision, revision_linkage is matched only on exact equality with the retrieved detail; mismatch is recorded as mismatch. If the arm did not expose a revision/hash, record not_exposed and do not claim search-time revision verification.
- A relevance label is unknown if the returned identity cannot be tied to retrieved detail, content is incomplete, or an arm-reported content hash/revision mismatches the detail. A detail fetched by exact stable ID with no search-time revision exposed may be judged for that retrieved revision only; report revision_linkage=not_exposed and do not describe it as revision-bound to the search-time observation.
- Audit linkage is verified only when the audit evidence explicitly matches the inspected content hash/revision. Missing, stale, mismatched, or unavailable audit data remain distinct states and never count as verified evidence.

Keep adjudication detail/audit lookups separate from data returned by either arm. These lookups do not change the selected three slots and do not give ordinary search credit for evidence it did not return. Keep full detail material local and ephemeral; do not store skill documents or evidence-packet excerpts in results.

For post-arm evidence retrieval, retain one shared **600-second (ten-minute) monotonic-clock budget per pair**. Start it immediately when the later of the two invoked arms reaches a terminal primary state: complete or partial valid response, returned operational error, harness failure, or harness-declared 240-second timeout. Record the UTC timestamp corresponding to the start and deadline for auditability. This budget is distinct from the 300-second invocation-start pairing window. A timeout is a terminal primary status even if underlying termination is `not_confirmed` or `unknown`; that uncertainty must remain recorded, and the stop-for-review rule still bars another invocation. If either arm was never invoked, do not run pair-level lookups; record candidate relevance as `unknown` with assessability reason `not_assessable`. A late primary response does not reset the budget or revise the primary result.

Within that budget, make at most one attempt per evaluation-only detail or audit lookup, with no retry. The fixed ordering is: arms in their assigned invocation order; candidates in ascending rank within each arm; detail before audit for each candidate. The offline recorder and process-isolated adapter follow this order. The adapter receives the absolute monotonic deadline, refuses dispatch at or after it, and limits the worker to the remaining budget; offline fake-worker tests cover this control, not live transport behavior. Continue after a lookup failure only when time remains and termination is confirmed; unknown or unconfirmed lookup termination stops further invocations pending review. This order gives the earlier arm and higher-ranked candidates priority if the deadline expires; report this ordering bias and do not interpret lower completion rates for later slots as irrelevance. Record every planned lookup, including one not started because the deadline arrived. Do not start any lookup at or after the monotonic deadline; responses completing after the deadline are supplemental only. Record monotonic and UTC start/end times, attempt count, HTTP status when received, sanitized error category, timeout and termination status, whether a response was late, returned candidate identity, content hash/revision, and linkage to the corresponding arm observation where available. Preserve only allowlisted response metadata such as Date, ETag, and request ID. Do not save full response bodies or skill documents.

The 600-second cutoff is an operational bound, not a service guarantee. A response completed after it is marked late and retained only as supplemental data; it is excluded from primary reviewer packets. Missing, failed, late, unlinked, identity-mismatched, or revision/hash-mismatched relevance evidence stays unknown or unverified as applicable and is never treated as irrelevant. A candidate may be relevance-assessable when its linked detail is sufficient to apply the task criterion even while its safety/audit status remains `unknown` or `unverified`. Missing, late, or mismatched audit evidence remains unknown/unverified and never implies safety or provides a safety clearance. Where an observed arm hash/revision is absent, record linkage as `not_exposed` and do not claim revision-bound evidence.

Do not claim that cancellation terminates an in-flight request. If termination is `not_confirmed` or `unknown` for any invoked operation, stop all further invocations pending human review. The adapter can confirm that its local worker exited after a timeout when reaping succeeds, but upstream request cancellation remains `not_confirmed`. Any later response is supplemental only. ## 4. Statuses, decisions, and timing measure

Operational status is separate from policy decision, candidate evidence, and relevance. Apply these arm-level statuses:

| Arm status | Definition |
|---|---|
| not_run | The arm was scheduled but never invoked, for example after a run stop. |
| blocked | The arm was not invoked because a required precondition was absent; record a reason such as approved_context_unavailable or credential_unavailable. |
| failed | The arm was invoked but produced no valid arm-level response, for example a non-success HTTP result, transport error, 240-second harness timeout, unexpected harness failure, or malformed response. Record `harness_timeout`/`harness_failure` separately from underlying-request termination (`confirmed`, `not_confirmed`, or `unknown`). |
| partial | The arm produced a parseable response that is explicitly marked partial/truncated or is missing part of its arm-level result. Do not infer partial from an absent optional field. Missing audit evidence, a valid REVIEW decision, or incomplete candidate evidence in an otherwise valid structured response are evidence states, not operationally partial responses. Malformed top-level responses are failed. |
| complete | The arm produced a valid response. A valid empty search and valid NO_SKILL_NEEDED are complete arm responses. |

Apply these pair-level rules:

| Pair status | Definition |
|---|---|
| not_run | Neither arm was invoked because the run stopped before this pair began; include the stop reason. |
| blocked | Neither arm was invoked because a shared prerequisite blocked the pair. |
| failed | Both arms were invoked and neither produced a valid primary arm-level response. |
| complete | Both arms produced complete primary responses and the second invocation started at or before 300 seconds after the first. |
| partial | Any other combination, including only one arm invoked, an absent/late second start, a failed/blocked/not_run arm paired with another status, a partial arm response, or a second start after 300 seconds. Preserve all observed results and do not fabricate absent invocation timestamps. |

A parseable `partial` arm response is an observed primary result and makes the pair `partial`. `failed` applies only when both arms were invoked, both have failed status, and neither produced a valid arm-level response. A single-arm failure, a valid response paired with failure, and an unstarted paired arm are `partial`.

A valid SkillScout response has an explicit nullable decision field whose value is exactly one of NO_SKILL_NEEDED, USE, REVIEW, or AVOID. It is null if SkillScout was not invoked or no valid structured response supplied a decision. The ordinary-search arm always has decision=null. Store operational status and error category/message in separate fields. A catalog failure is never a no-skill outcome, and an empty valid search is not an HTTP/tool failure.

Candidate detail, audit, compatibility, scanner, and inspection completeness are candidate evidence fields, not arm decisions. A complete arm response can still contain REVIEW or incomplete candidate evidence. Do not imply that a clean heuristic scan proves safety.

Keep the metric name **Time to useful decision (TUD)** and use `evidence_ready` to mean ready for candidate-relevance judgment. For each arm with a complete primary response, `evidence_ready` is the later of (a) receipt of that response and (b) availability, for every occupied candidate slot, of complete detail whose identity is linked to the returned candidate and whose content is sufficient to apply the unchanged task-specific relevance criterion. Per-arm TUD is the monotonic duration from invocation start to that event. For a valid empty result or valid `NO_SKILL_NEEDED` with no candidates, `evidence_ready` and TUD end when the valid primary response arrives. A partial primary response may contain individually assessable candidates, but arm-level `evidence_ready` and TUD remain incomplete because the primary result is incomplete and absent/truncated positions remain unknown. If required relevance evidence is missing, failed, late, unlinked, mismatched, or otherwise insufficient at the 600-second cutoff, TUD is censored/incomplete; do not report the cutoff as a successful decision time. A timeout or harness failure is failed/incomplete, never success. This is a relevance-evidence endpoint, not a time to safety clearance.

Safety/audit evidence is tracked separately and is not required for relevance `evidence_ready`. A candidate can be relevance-assessable while its safety/audit status is `unknown` or `unverified`; that relevance assessment does not imply safety or validate a safety-dependent policy decision. Missing, late, or mismatched audit evidence remains unknown/unverified.

Report these timing components separately, using monotonic durations and UTC event timestamps:

- **Arm response latency:** invocation start to the primary valid response or terminal operational status (including timeout/error). It is not evidence-retrieval time and does not imply success.
- **Evidence-retrieval duration:** elapsed time spent in the shared post-arm lookup phase, reported per arm and pair; identify lookup start, last primary completion, or deadline expiry.
- **Waiting attributable to the paired arm:** for the arm that reaches a terminal primary state first, the interval from its terminal state until the other invoked arm reaches its terminal primary state. It is zero/not applicable for an arm with no such wait.
- **Pair-level time to evidence-ready:** the monotonic duration from the first invocation start until both arms have reached `evidence_ready` as defined above. It may include the inter-arm wait and shared lookup phase. If either arm is not invoked, report it as not assessable; if either arm lacks a complete primary response or required relevance evidence is not ready by the cutoff, report it as incomplete/censored. Do not report a successful time in either case.

Because lookups begin only after both invoked arms reach terminal primary states, TUD for the earlier-finishing arm and pair-level time-to-evidence-ready may include waiting imposed by the paired execution. Report that wait separately; do not interpret TUD as intrinsic, isolated model or service latency. The offline recorder records these components in mocked runs; that does not establish live adapter enforcement or runtime behavior.

### Slot accounting and interpretation

For each arm, the fixed-slot denominator is 126 planned top-three positions (14 eligible tasks × 3 repetitions × 3 positions). Before collection, report the exact denominators and count each position once: `relevant`, `irrelevant`, `unknown` (occupied candidate but evidence cannot support a relevance judgment), `unresolved_review` (no final label because review/adjudication is unresolved), `empty` (a valid completed response returned fewer than three candidates), `failed` (invoked but no valid primary response), `blocked`, or `not_run`. A parseable partial response's absent/truncated positions are `unknown`, not empty. An occupied, unresolved review is not silently converted to candidate relevance `unknown`.

Use the slot categories above in every summary and show arm/repetition counts. The 42 pairs are repeated observations clustered within 14 tasks, not 42 independent tasks; treat the 14 tasks as interpretation units and report repetition and arm-order effects descriptively.

### Primary estimand and complete-pair sensitivity

The primary metric is **confirmed relevant-slot yield@3 per planned slot**. For task `i` (14 eligible tasks), arm `a` (`SkillScout` or `ordinary search`), and repetition `r` (three per task), define `R_iar` as the count from 0 to 3 of planned top-three slots occupied by a candidate in a valid primary response, with complete identity-linked detail sufficient to apply the unchanged task relevance criterion available by the shared 600-second deadline, and a final resolved candidate relevance label of `relevant`. Evidence or responses arriving after the applicable primary deadline are supplemental and do not count.

For each task, arm, and repetition calculate `q_iar = R_iar / 3`; the three planned positions are the denominator even when the arm fails, is blocked, is not run, returns an empty result, or lacks assessable evidence. For repetition `r`, calculate `d_ir = q_i,SkillScout,r - q_i,ordinary,r`. First average repetitions within task, `D_i = (d_i1 + d_i2 + d_i3) / 3`, then average task means equally, `Delta = sum(D_i, i=1..14) / 14`. Report `Delta` as the SkillScout-minus-ordinary-search difference in confirmed relevant-slot yield@3 per planned slot. The fixed denominator is 3 planned slots per arm per repetition and 126 slots per arm across all 14 tasks.

A failed, blocked, or uninvoked arm contributes zero confirmed relevant slots (`R_iar = 0`) but its planned positions are not labeled irrelevant. A valid empty response contributes no relevant slots and its returned-empty positions remain `empty`. A parseable partial response may contribute a returned candidate slot only if that slot meets the primary-response, timely-detail, and final-label conditions; absent or truncated positions remain `unknown`. Occupied unknown or unresolved-review slots add no numerator and remain separately reported. Do not drop incomplete pairs from the primary estimate. This estimand describes confirmed end-to-end yield over the fixed planned slots, not precision conditional on successful inspection.

Predeclare complete-pair sensitivity eligibility as follows. A task/repetition qualifies only when both arms were invoked, both produced valid complete primary responses within their 240-second caps, the second invocation started at or before the 300-second pairing boundary, and every occupied candidate slot has complete, identity-linked detail sufficient to apply the task relevance criterion by the shared 600-second deadline. A valid complete empty response satisfies the evidence condition without candidate detail. Apply the rule using only invocation, response, timing, and evidence-completeness/linkage fields before relevance labels or comparative results are considered. Do not use label values, review resolution, expected outcomes, or observed system differences to select eligible pairs. Apply the same fixed three-slot denominator to eligible repetitions. For each task with at least one eligible repetition, average its eligible repetition differences; then average those task means equally. Report eligible repetitions per task, the number of contributing tasks, and tasks with no eligible repetitions. Unknown or unresolved labels stay unconfirmed in this sensitivity calculation and are reported separately; this analysis does not replace the primary estimate.

### Decision-conformity outcomes and evidence gates

Candidate relevance and task-level decision conformity answer different questions. Candidate relevance labels an identity-linked candidate revision against the unchanged task criterion. Decision conformity asks whether SkillScout's task-level action is justified by the task requirements and sufficient evidence. A relevant candidate can still fail to justify `USE` if compatibility, integration requirements, or a required safety/audit gate is not established. Conversely, `NO_SKILL_NEEDED` may be justified when a relevant but optional candidate adds no material task-specific value. The exact materiality threshold remains unresolved and requires human approval.

| Decision | Evidence required for a justified action | Limits on interpretation |
|---|---|---|
| `NO_SKILL_NEEDED` | The exact task and approved context support that the work is self-contained, or adequate assessment of the relevant candidate set supports that no candidate adds material task-specific value. If the rationale depends on the absence of useful candidates, primary results and required candidate evidence must be sufficiently complete to support that conclusion. | A valid empty result, failed search, missing detail, or incomplete candidate set alone does not prove that no skill is needed. A potentially relevant but optional candidate does not by itself make this decision incorrect. The task-specific materiality and evidence-completeness thresholds need human approval. |
| `USE` | At least one candidate is tied to its exact inspected identity/revision; its contents materially address the task; applicable compatibility and integration requirements are supported; and every safety/audit gate required for that task is affirmatively met. | Candidate relevance alone is insufficient. Unknown or unverified mandatory compatibility, integration, or safety evidence does not pass a gate. This recommendation never authorizes installation or execution. The exact per-task mandatory gates remain subject to human approval. |
| `REVIEW` | A plausible task-relevant candidate exists and a specific, decision-critical uncertainty or conflict could change the appropriate action and warrants review under the task requirements. The uncertainty must be visible in the task rule or in information actually available to SkillScout at decision time. | An evaluator-only lookup failure or missing fact discovered only after the response does not establish that SkillScout knew of the uncertainty. `REVIEW` is not a substitute for an operational failure, null decision, or absent candidate evidence. The threshold for when uncertainty warrants review remains subject to human approval. |
| `AVOID` | Affirmative evidence establishes a current critical or prohibited risk tied to the exact candidate and inspected revision, with evidence linkage sufficient to support that risk. | Missing, stale, unlinked, mismatched, or unavailable audit evidence is not evidence of danger and cannot alone justify `AVOID`. Generic popularity, rank, or scanner warnings alone are insufficient. The criticality threshold and what counts as a qualifying finding require human approval. The excluded synthetic critical-risk task means this study cannot establish `AVOID` sensitivity or reliability. |

#### Decision-time versus retrospective evaluator evidence

For each decision, keep two evidence records distinct. **Decision-time evidence** is the exact task text, approved pinned context, and information actually returned or surfaced to SkillScout before its decision. It can establish what information was available to support the action; do not infer that SkillScout knew a fact merely because an evaluator later found it. **Retrospective evaluator evidence** is identity- and, where exposed, revision-linked detail or audit material collected under the existing shared 600-second lookup budget. It may verify candidate contents or a fact about the inspected revision, but it does not prove that the fact was available to SkillScout at decision time. Evidence after the existing deadline remains supplemental and cannot change the primary assessment.

`CORRECT` requires a valid non-null SkillScout decision, sufficient task/context and decision-relevant evidence, and a resolved independent review showing that the decision matches the justified action. `INCORRECT` requires the same assessability conditions and sufficient evidence for a different justified action. Use `INDETERMINATE` when the record cannot distinguish these outcomes. In particular, if a conclusion depends on whether a fact was available at decision time and that provenance is not established, do not infer it from retrospective evidence; mark the result `INDETERMINATE`. Exact decision-time provenance rules remain a human approval item.

Missing, late, stale, identity- or revision-mismatched, conflicting, or insufficient evidence stays unknown/unverified and cannot be treated as irrelevant, safe, or unsafe. A missing required fact does not pass a `USE` gate; its absence alone does not justify `AVOID`. A parseable partial response with a valid decision may be scored only if the evidence needed to judge that decision is sufficient despite the partial status. A timeout, unexpected harness failure without a valid decision, blocked or uninvoked SkillScout arm, or null/invalid decision has no assessable action and is `INDETERMINATE`; preserve its operational result separately. If one arm in the pair fails, that alone does not erase an otherwise assessable SkillScout decision, but the pair status and evidence availability remain separately reported. If either arm was never invoked, the existing protocol prohibits pair-level lookups; evaluator evidence unavailable as a result cannot be assumed. A valid empty SkillScout result can support `NO_SKILL_NEEDED` only where task/context evidence independently supports that action; emptiness alone is not sufficient. Late evidence is supplemental only and does not backfill a primary judgment.

The priority rule when more than one action appears supportable (for example, a candidate may be useful while a required safety fact is unknown) is not fully specified. Do not resolve such conflicts by post-hoc reviewer discretion; agree and document any precedence rule before data collection. Also obtain human approval for each task's materiality and compatibility/integration thresholds, the list of mandatory safety/audit gates, the threshold and scope of `AVOID`, and whether correctness is judged strictly from decision-time support or from a separately authorized retrospective fact standard.

## 5. Blinded human review

The offline packet builder supports two independent primary reviewers for each task-specific candidate revision. Reviewer availability has not been confirmed, and use in the study remains subject to human approval. Each blinded candidate-review packet contains the exact task text, unchanged relevance criterion, approved context description scrubbed of expected-outcome disclosures, and candidate detail content needed to assess relevance. It excludes system/arm identity, system decisions, task-level expected labels/categories/decisions, candidate ranks or other rankings, scores, popularity, protected safety/audit findings, scanner findings, and the reviewer crosswalk. For `review-stripe-webhook-audit`, the evaluator-only audit-state phrase and equivalent direct or indirect disclosure are rejected by packet construction. Fixture descriptions and context summaries must not disclose the expected outcome indirectly. Stable candidate IDs supplied for masking and source URLs are removed where feasible. Candidate content or unavoidable metadata may identify a source; record what was exposed and each reviewer's source recognition, and report the exposure as a blinding limitation. Source recognition from content alone does not automatically invalidate a label. Packet construction and ledger tests are offline software tests, not evidence of human blinding performance.

If protected metadata is accidentally exposed, record the affected task/candidate and reviewer, the metadata exposed, and when exposure occurred relative to the label/adjudication. Preserve the original assessment and reason, mark blinding `compromised`, and do not present it as fully blinded. Obtain an independent replacement from an unexposed reviewer if available; otherwise the review resolution is `unresolved`. Apply the same rule to a third reviewer exposed before locking the independent assessment. No reviewer availability is assumed.

Generate an opaque candidate key for each task-specific candidate revision and shuffle review order with a recorded seed before review. The separate reviewer crosswalk has one row per occurrence, linking opaque key and task ID to pair/repetition, arm, rank, stable ID, source URL, and candidate content hash/revision. Store it separately with access restricted from reviewers until all blinded primary labels and any adjudication are locked. Do not include arm, rank, stable candidate ID, or source URL in reviewer-facing files where feasible; if a field cannot be masked without destroying reviewability, record it as unavoidable exposure.

Duplicate reuse is allowed only for the same task ID and same stable ID plus exact content hash/revision. That candidate revision may be reviewed once for that task and its label reused across arms/repetitions in that task. Review the same content revision independently for different tasks because the task and criteria differ. Different hashes are separate revisions. If no content hash is available, do not deduplicate on identity alone. Incomplete or untied content is unknown.

Each primary reviewer independently records candidate relevance `relevant`, `irrelevant`, or `unknown`, a short criterion-linked reason, source/system recognition, and blinding status. `Unknown` means the candidate evidence is insufficient, incomplete, unlinked, or mismatched to judge relevance. Record review resolution separately as `resolved` or `unresolved`; unresolved disagreement/adjudication or a compromised review without replacement is not a candidate relevance label and must not be recoded as `unknown`. If both valid blinded reviewers agree, preserve both records and use the agreed label. If they disagree, lock both initial reviews before the third reviewer sees the packet. The third reviewer first locks an independent blinded label/reason without seeing initial labels/reasons, then sees the two locked reviews and records separate adjudication without system, rank, or crosswalk. Preserve every assessment and rationale. If adjudication is unavailable, the final review resolution remains unresolved. If evidence itself is insufficient under Section 3, candidate relevance is `unknown` regardless of reviewer preference. Do not average labels or use SkillScout outputs as ground truth.

### Separate independent task-level decision-conformity review

This is a distinct review from candidate-relevance labeling.
