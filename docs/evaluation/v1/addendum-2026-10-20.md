### Proposed fixture setup and hashing

If approved, use one checked-in directory per task beneath docs/evaluation/v1/contexts/<task-id>/. Use the same pinned, read-only context for both arms and all three repetitions. Do not install packages, execute project code, access databases/cloud accounts, follow symlinks, or include special files.

The proposed MANIFEST.sha256 is generated from fixture files only and excludes itself:

1. Include every regular file beneath that task's fixture directory except the root-level MANIFEST.sha256 itself. Reject symlinks and non-regular files; do not silently omit hidden files.
2. Require relative paths to be valid UTF-8, normalized to Unicode NFC, free of "." or ".." components, and without control characters or line breaks. Serialize each path using POSIX "/" separators.
3. Sort paths by their UTF-8 byte sequence.
4. For each file, write lowercase SHA-256 of its exact bytes, two ASCII spaces, the relative POSIX path, and one LF byte.
5. Encode the manifest as UTF-8. Record its SHA-256 and the Git commit containing the fixture pack. Do not include the manifest in its own input file set.

Record the task context reference and manifest hash in the run manifest; no absolute user paths are required. These proposed fixture packs are synthetic project contexts, not real developer projects. A real repository pinned to a commit is an alternative only if its owner, exact revision, and task-specific context are approved. No repository is selected.

The exact task field from tasks.jsonl is the query in both arms. Do not append project_context or rewrite the task. The project context is supplied separately. Do not report context facts as SkillScout-detected unless its response actually contains them.

## 2. Primary comparison and baseline request

The primary comparison is an **end-to-end product comparison**, not a test isolating ranking quality.

For the ordinary-search arm, issue one initial request:

    GET https://skills.sh/api/v1/skills/search?q=<UTF-8 percent-encoded exact task field>&limit=3
    Accept: application/json
    Authorization: Bearer <authorized token supplied through the documented process environment>

Use the exact task string; do not add project_context, filters, or install-count sorting. Select the first three entries in the response data array, in returned order. Do not rerank, deduplicate, filter, or backfill. Fewer than three entries remain fewer occupied slots. Make exactly one baseline search request per planned attempt in this primary experiment: no automatic retry. A 401/403, other non-success status, timeout, malformed response, or transport error is recorded as a failed observation, never as an empty search or negative relevance result. Any retry comparison is a separate future experiment with its own approval and results.

The SkillScout arm uses MCP prepare_task, agent=codex, the same exact task field, the approved task context, optional LLM disabled, and SKILLSCOUT_CANDIDATE_LIMIT=3. Return its first three recommendations in SkillScout rank order. A valid NO_SKILL_NEEDED response is a SkillScout decision, not a catalog failure.

SkillScout's existing retrieval pipeline searches a larger pool before ranking. In the current implementation, a candidate limit of three produces a catalog search limit of 18 (min(50, max(10, candidate_limit * 6))) before SkillScout returns up to three ranked candidates. The ordinary baseline returns the catalog's first three directly. This unequal retrieval pool is intentional for the proposed end-to-end product comparison. It means observed differences can reflect retrieval, ranking, policy, and inspection together; results must not be described as isolating ranking quality or as a ranking-only comparison. Do not change SkillScout's retrieval behavior for this evaluation.

Use the documented supported authentication flow for both arms, with an authorized credential supplied to the process environment. Never put credential values in the URL, task, shell history, MCP configuration, raw records, or reviewer material. No credential is accessed or requested by this addendum.

### Proposed arm invocation cap — pending human approval

Propose a maximum wall-clock duration of **240 seconds per arm invocation**, measured from its invocation start to receipt of a valid response or a terminal error. This is a proposed operational cap, not a measured service guarantee. The rationale is to leave up to 60 seconds within the existing 300-second start window to dispatch the second arm if the first reaches its cap; no service or evaluation data has validated this value. The cap may terminate waiting for SkillScout's existing multi-request and retry workflow before it completes, so the owner must explicitly accept or replace the value before protocol freeze. No runner currently enforces the cap; its enforcement and ability to proceed after the caller stops waiting remain unverified.

Have the evaluation harness issue arm invocations sequentially in the assigned order. Start the second invocation immediately after the first returns a valid response, returns an error, or reaches the 240-second cap. A first-arm error or timeout does not cancel the scheduled second arm. Because cancellation is unverified, a timed-out underlying call may continue and overlap the second arm; the protocol does not claim that network activity is serialized or terminated. If the second start is more than 300 seconds after the first start, still retain the second-arm attempt and mark the pair window exceeded and pair status partial under the existing rules. If the harness cannot proceed to the second invocation after its first-arm wait reaches the cap, record the second arm as not_run and the pair as partial; do not extend the cap or invent a response.

At the cap, record the arm as `failed` with error code `invocation_timeout`, no valid arm-level response, and a null SkillScout decision if it was the SkillScout arm. A timeout is an operational failure, never a successful or useful decision. Preserve the elapsed time as failed/incomplete for **Time to useful decision**; do not count 240 seconds as a successful decision time. Under this proposal, the evaluation harness stops waiting for the primary result at the cap, but this alone does not prove that the underlying MCP call, process, or HTTP request has stopped. Do not claim cancellation. If a response arrives after the cap, retain it only as a late supplemental observation; it does not revise the primary arm status or decision.

Apply the existing pair-status rules: if both arms were invoked and neither produced a valid primary response, the pair is `failed`; if one produced a valid response and the other timed out or failed, the pair is `partial`. A timeout or missing result never becomes `NO_SKILL_NEEDED` or an empty successful search.

This five-minute window limits elapsed time between arm invocation starts; it does not create a shared catalog snapshot. Record catalog-provided Date, ETag, and request identifiers when actually returned, plus stable IDs, observed revisions/hashes, audit timestamps, and the time each detail/audit was retrieved. No snapshot consistency may be claimed solely from timestamps or matching identities.

For each returned candidate, record:
- The exact stable ID (source/slug), arm, and rank.
- Detail identity, detail retrieval status, content hash, revision if exposed, and retrieval time.
- Whether the detail can be tied to the search/tool observation: identity_linkage is matched only when the stable ID exactly matches; otherwise it is unverified. If the arm exposed a content hash/revision, revision_linkage is matched only on exact equality with the retrieved detail; mismatch is recorded as mismatch. If the arm did not expose a revision/hash, record not_exposed and do not claim search-time revision verification.
- A relevance label is unknown if the returned identity cannot be tied to retrieved detail, content is incomplete, or an arm-reported content hash/revision mismatches the detail. A detail fetched by exact stable ID with no search-time revision exposed may be judged for that retrieved revision only; report revision_linkage=not_exposed and do not describe it as revision-bound to the search-time observation.
- Audit linkage is verified only when the audit evidence explicitly matches the inspected content hash/revision. Missing, stale, mismatched, or unavailable audit data remain distinct states and never count as verified evidence.

Keep adjudication detail/audit lookups separate from data returned by either arm. These lookups do not change the selected three slots and do not give ordinary search credit for evidence it did not return. Keep full detail material local and ephemeral; do not store skill documents or evidence-packet excerpts in results.

For reproducible, post-arm evidence retrieval, when both arms have been invoked, start one shared ten-minute wall-clock budget for the pair when the later arm reaches a terminal primary state: valid response, returned operational error, or harness-declared 240-second invocation timeout. A late response after a declared timeout does not reset the clock or enter the primary arm result. This deadline is separate from the five-minute window between invocation start times; the former bounds evidence lookups after both primary arm attempts finish, while the latter bounds the spacing of the two arm starts. The ten-minute budget is shared across all evaluation-only detail and audit lookups for the pair and is not reset for each candidate or request. If an arm is blocked or not_run and therefore never invoked, do not start this post-arm lookup phase.

Within that budget, make at most one attempt for each evaluation-only detail or audit lookup, with no retry. Traverse arms in their invocation order, candidates in ascending rank within each arm, and for each candidate request detail before audit. Continue to the next scheduled lookup after a failure if time remains. Record every planned lookup, including one not started because the deadline arrived. Do not start new lookups at or after the deadline. Record request-start and response/end timestamps, attempt count, HTTP status when received, sanitized error category/message, timeout status, cancellation requested/status, whether a response was late, returned candidate identity, content hash/revision, and linkage to the corresponding arm observation where available. Preserve response metadata such as Date, ETag, and request ID when returned. Do not save full response bodies or skill documents.

The ten-minute cutoff is an operational bound, not a service guarantee. A response completed after it is marked late and retained only as supplemental data; it is excluded from primary reviewer packets. Missing, failed, late, unlinked, identity-mismatched, or revision/hash-mismatched evidence stays unknown or unverified as applicable and is never treated as negative relevance or as evidence of safety. If no detail is available by the cutoff, primary relevance is unknown. An audit that is unavailable, late, or unlinked remains an unknown audit state; it does not become a negative relevance label or a safety clearance. Where an observed arm hash/revision is absent, record linkage as not_exposed and do not claim revision-bound evidence.

Do not claim that cancellation terminates an in-flight HTTP request. Cancellation is a technical requirement, not yet verified: the implementation must be tested to establish that the underlying request/connection terminates, rather than merely stopping the caller from awaiting it. Until such a test passes, mark cancellation as unverified; if a request continues and returns after the deadline, record it as late supplemental evidence. The ten-minute deadline must still bound primary evidence inclusion even if the transport cannot be interrupted.

SkillScout's ordinary product workflow retains its configured retry behavior. The current catalog client defaults to two retries after the initial attempt (up to three attempts for retryable failures); this is not changed for the evaluation. Record attempts when observable, otherwise use unknown. Evaluation-only post-arm detail/audit lookups use a separate one-attempt/no-retry path. This intentional operational asymmetry must be disclosed with results; the ordinary-search baseline also remains exactly one initial request with no retry. These evaluation-only rules do not change normal product behavior.

## 4. Statuses, decisions, and timing measure

Operational status is separate from policy decision, candidate evidence, and relevance. Apply these arm-level statuses:

| Arm status | Definition |
|---|---|
| not_run | The arm was scheduled but never invoked, for example after a run stop. |
| blocked | The arm was not invoked because a required precondition was absent; record a reason such as approved_context_unavailable or credential_unavailable. |
| failed | The arm was invoked but produced no valid arm-level response, for example a non-success HTTP result, transport error, timeout, or malformed response. |
| partial | The arm produced a parseable response that is explicitly marked partial/truncated or is missing part of its arm-level result. Do not infer partial from an absent optional field. Missing audit evidence, a valid REVIEW decision, or incomplete candidate evidence in an otherwise valid structured response are evidence states, not operationally partial responses. Malformed top-level responses are failed. |
| complete | The arm produced a valid response. A valid empty search and valid NO_SKILL_NEEDED are complete arm responses. |

Apply these pair-level rules:

| Pair status | Definition |
|---|---|
| not_run | Neither arm was invoked because the run stopped before this pair began; include the stop reason. |
| blocked | Neither arm was invoked because a shared prerequisite blocked the pair. |
| failed | Both arms were invoked and neither produced a valid arm-level response. |
| complete | Both arms are complete and invocation starts are within 300 seconds. |
| partial | Every other combination: one arm is complete and the other is failed/blocked/not_run/partial; either arm is partial; only one arm was invoked; or both otherwise-valid arms are outside the pairing window. |

A valid SkillScout response has an explicit nullable decision field whose value is exactly one of NO_SKILL_NEEDED, USE, REVIEW, or AVOID. It is null if SkillScout was not invoked or no valid structured response supplied a decision. The ordinary-search arm always has decision=null. Store operational status and error category/message in separate fields. A catalog failure is never a no-skill outcome, and an empty valid search is not an HTTP/tool failure.

Candidate detail, audit, compatibility, scanner, and inspection completeness are candidate evidence fields, not arm decisions. A complete arm response can still contain REVIEW or incomplete candidate evidence. Do not imply that a clean heuristic scan proves safety.

Keep the original metric name **Time to useful decision**. The proposed operational endpoint starts at arm invocation start and stops when the detail material required for a human to judge all returned candidate slots is available. For a valid empty candidate set or valid NO_SKILL_NEEDED with no candidates, stop when the valid arm response is available because no candidate detail is needed. Record arm response/tool latency and detail-retrieval duration separately so this endpoint can be audited. If useful detail is unavailable by the ten-minute post-arm cutoff, record the metric as censored/incomplete under this endpoint; do not count reaching the cutoff as a successful decision or substitute ten minutes as a success time. Errors and incomplete results retain elapsed time as failures/incomplete observations, not as successful fast decisions. This adopts an operational endpoint for the existing metric; it does not add or rename a metric. Report the interpretation with results.

## 5. Blinded human relevance review

The proposed review uses two independent primary reviewers for each task-specific candidate revision. Reviewer availability has not been confirmed. Each blinded reviewer packet contains only the exact task text, its unchanged criterion, approved context description, and candidate detail material. It must hide arm/system, rank, SkillScout score/decision, popularity, audit, and scanner findings. The reviewer crosswalk is inaccessible to reviewers. Candidate text may inherently reveal its source; reviewers record source/system recognition, which is reported as a limitation but does not by itself invalidate a label.

If protected metadata is accidentally exposed, record the affected task/candidate and reviewer, what was exposed, and when relative to the label or adjudication. Preserve the original assessment and reason, mark its blinding status compromised, and do not present it as a fully blinded assessment. Obtain a replacement independent assessment from an unexposed reviewer if one is available. If none is available, retain the compromised assessment and mark the affected blinded judgment unresolved. If a third reviewer is exposed to protected metadata before locking their independent label or adjudication, mark that assessment compromised and seek an unexposed replacement; if unavailable, adjudication is unresolved. No reviewer availability is assumed.

Generate an opaque candidate key for each task-specific candidate revision and shuffle review order with a recorded seed before review. The separate reviewer crosswalk has one row per occurrence, linking opaque key and task ID to pair/repetition, arm, rank, stable ID, and candidate content hash/revision. Store it separately with access restricted from reviewers until all blinded primary labels and any adjudication are locked. Do not include arm/rank in reviewer-facing files.

Duplicate reuse is allowed only for the same task ID and same stable ID plus exact content hash/revision. That candidate revision may be reviewed once for that task and its label reused across arms/repetitions in that task. Review the same content revision independently for different tasks because the task and criteria differ. Different hashes are separate revisions. If no content hash is available, do not deduplicate on identity alone. Incomplete or untied content is unknown.

Each primary reviewer independently records the unchanged label relevant, irrelevant, or unknown, a short criterion-linked reason, a source-recognition flag, and blinding status. If both agree, preserve both records and use the agreed label. If they disagree, lock and preserve both initial reviews before the proposed third reviewer receives the same blinded packet. The third reviewer first records and locks an independent blinded label and reason without seeing the initial labels or reasons. Only after that assessment is locked may the third reviewer see the two initial labels and reasons, then record a separate adjudication label and rationale without seeing system, rank, or crosswalk. Preserve all assessments and reasons. The adjudicated label is final. If adjudication is unavailable, preserve the two primary reviews and leave the final label unresolved; do not silently convert this to agreement or unknown. If evidence is incomplete or untied under Section 3, final relevance is unknown regardless of reviewer preference. Do not average labels or use SkillScout outputs as ground truth.

This reviewer procedure and third-reviewer decision rule are proposals requiring owner approval. No reviewer assignment or availability is asserted.

Blinded judgments are a separate JSONL file keyed by opaque candidate key and task ID, with reviewer pseudonym, individual label, criterion-linked reason, source-recognition flag, blinding status/deviation, and final/adjudication outcome. The crosswalk is a separate restricted file with one row per occurrence linking opaque key to pair/repetition, task, arm, rank, stable identity, and revision. Keep it inaccessible to reviewers; the third reviewer sees the locked initial labels/reasons only after locking their own independent blinded assessment. Store summaries only as derivations of the raw records. Keep live, mocked, offline, and synthetic records distinguishable; a live-catalog run with synthetic project contexts must be labeled live catalog plus synthetic context, not a real-project study.

The recorder and validator may be implemented only after protocol-owner approval. Their schema and validation behavior require a separate review before any run records are collected.

## 7. Approval and execution gates

The following are still proposed and require explicit owner approval:

1. The end-to-end estimand: ordinary first three search results versus SkillScout's existing larger retrieval pool and ranked top three; acknowledge that this does not isolate ranking quality.
2. One no-retry baseline request, the fixed 42-pair schedule and repetition-major execution order, sequential invocation handling, the invocation-start five-minute pairing rule, and the proposed 240-second cap and its arm/pair timeout accounting, including the possibility of underlying requests continuing after the harness wait ends.
3. The shared ten-minute post-arm evidence deadline, one-attempt evaluation-only detail/audit lookups, lookup order, late-evidence handling, and the asymmetry with SkillScout's normal retry behavior.
4. The evidence-linkage/unknown rules, arm and pair statuses, nullable decision field, raw records, and restricted reviewer crosswalk.
5. The timing endpoint and censored/incomplete handling for the existing Time to useful decision metric.
6. The two-reviewer blinding requirements, source-recognition and protected-metadata breach handling, third-reviewer independent-before-adjudication sequence, adjudicated-final-label rule, and unresolved outcome if adjudication is unavailable. Reviewer availability remains unconfirmed.
7. Each of the 14 fixture contexts in Section 1, including resolution of the unspecified test framework, test command, PostgreSQL schema/workload, and Terraform policy/trust contents. Until each context is approved, created, hashed, and pinned, that task remains blocked.
8. Authorized catalog access through the documented process environment before any future live validation. Availability has not been checked or confirmed by this proposal.
9. The lookup-cancellation implementation requirement and test evidence. Hard cancellation remains unverified until a test confirms termination of the underlying request/connection.

After those approvals, the evaluation owner must separately approve recorder implementation and then authorize any live collection. Until the required context is pinned and authorized catalog access is available, no task is runnable for the live paired study. This proposal itself authorizes neither fixture creation, recorder implementation, catalog requests, nor data collection.
