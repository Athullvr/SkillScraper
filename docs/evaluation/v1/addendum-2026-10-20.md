### Proposed fixture setup and hashing

If approved, use one checked-in directory per task beneath docs/evaluation/v1/contexts/<task-id>/. Use the same pinned, read-only context for both arms and all three repetitions. Do not install packages, execute project code, access databases/cloud accounts, follow symlinks, or include special files.

The proposed MANIFEST.sha256 is generated from fixture files only and excludes itself:

1. Include every regular file beneath that task's fixture directory except the root-level MANIFEST.sha256 itself. Reject symlinks and non-regular files; do not silently omit hidden files.
2. Require relative paths to be valid UTF-8, normalized to Unicode NFC, free of "." or ".." components, and without control characters or line breaks. Serialize each path using POSIX "/" separators.
3. Sort paths by their UTF-8 byte sequence.
4. For each file, write lowercase SHA-256 of its exact bytes, two ASCII spaces, the relative POSIX path, and one LF byte.
5. Encode the manifest as UTF-8. Record its SHA-256 and the Git commit containing the fixture pack. Do not include the manifest in its own input file set.

Record the task context reference and manifest hash in the run manifest; no absolute user paths are required. These proposed fixture packs are synthetic project contexts, not real developer projects. A real repository pinned to a commit is an alternative only if its owner, exact revision, and task-specific context are approved. No repository is selected.

Make exactly one baseline search request per planned attempt in this primary experiment: no automatic retry. The candidate limit, effective search-pool size, baseline limit/order, LLM state, and retry counts require runtime verification against the pinned revision before collection. ### Approved arm invocation cap policy; runtime enforcement unverified

Retain a maximum wall-clock duration of **240 seconds per arm invocation**, measured from the invocation-start event until a valid response or terminal error. If the first arm reaches the cap and termination is confirmed, the remaining 60 seconds in the 300-second pairing interval are only a nominal dispatch margin for starting the second arm; dispatch delay consumes that margin. This approved policy is not a measured service guarantee. This protocol supplies no runtime evidence that a runner enforces it. It may time out SkillScout's multi-request/retry workflow. Before collection, verify that the pinned runner actually applies the cap and records its outcome.

Record harness outcome separately from underlying-request termination. Use `confirmed`, `unconfirmed`, or `unknown` for termination status, with supporting evidence; a harness stopping its wait is not proof that the process, MCP call, transport, or HTTP request stopped. Do not claim cancellation without evidence of termination. A cap expiration is `failed`/incomplete with `invocation_timeout`, no valid primary result, and a null SkillScout decision if no valid decision was received. It is never a successful decision. Preserve a response received after the cap only as supplemental late evidence; it does not revise the primary status or decision.

Invoke arms sequentially in assigned order. If the first arm times out and underlying termination is unconfirmed or unknown, stop the run for human review; do not start the second arm or any subsequent invocation while an earlier request may still be active. Record the unstarted arm as `not_run`, without a fabricated start time, and the pair as `partial`. Resume only after review resolves whether continuation is safe. If a timeout's underlying termination is confirmed, the second arm may be attempted; its start must still be at or before 300 seconds to count as within-window. A late response remains supplemental and does not restart a stopped run automatically.

This stop-for-review rule halts subsequent arm invocations. If both arms have already been invoked and reached terminal primary states, apply the shared pair-level lookup budget below; if either arm was never invoked, run no pair-level lookups.

For an unexpected harness failure, record `harness_failure`, the last verified event/time, and any observed underlying-request termination status. Keep any valid response already received as that arm's primary response; for an invocation without a valid response, record `failed` and a null decision, never a fabricated value. If the harness failed before an invocation started, mark that arm `not_run` and leave its start time absent. Stop the run for review when it is unclear whether an in-flight request continues.

A timeout, harness failure without a valid response, or missing result never becomes `NO_SKILL_NEEDED`, an empty successful search, or a successful TUD observation. Pair classification is defined in Section 4.

The five-minute window limits elapsed time between arm invocation starts; it does not create a shared catalog snapshot. Record catalog-provided Date, ETag, and request identifiers when actually returned, plus stable IDs, observed revisions/hashes, audit timestamps, and each detail/audit retrieval time. No snapshot consistency may be claimed solely from timestamps or matching identities.

For each returned candidate, record:
- The exact stable ID (source/slug), arm, and rank.
- Detail identity, detail retrieval status, content hash, revision if exposed, and retrieval time.
- Whether the detail can be tied to the search/tool observation: identity_linkage is matched only when the stable ID exactly matches; otherwise it is unverified. If the arm exposed a content hash/revision, revision_linkage is matched only on exact equality with the retrieved detail; mismatch is recorded as mismatch. If the arm did not expose a revision/hash, record not_exposed and do not claim search-time revision verification.
- A relevance label is unknown if the returned identity cannot be tied to retrieved detail, content is incomplete, or an arm-reported content hash/revision mismatches the detail. A detail fetched by exact stable ID with no search-time revision exposed may be judged for that retrieved revision only; report revision_linkage=not_exposed and do not describe it as revision-bound to the search-time observation.
- Audit linkage is verified only when the audit evidence explicitly matches the inspected content hash/revision. Missing, stale, mismatched, or unavailable audit data remain distinct states and never count as verified evidence.

Keep adjudication detail/audit lookups separate from data returned by either arm. These lookups do not change the selected three slots and do not give ordinary search credit for evidence it did not return. Keep full detail material local and ephemeral; do not store skill documents or evidence-packet excerpts in results.

For post-arm evidence retrieval, retain one shared **600-second (ten-minute) monotonic-clock budget per pair**. Start it immediately when the later of the two invoked arms reaches a terminal primary state: complete or partial valid response, returned operational error, harness failure, or harness-declared 240-second timeout. Record the UTC timestamp corresponding to the start and deadline for auditability. This budget is distinct from the 300-second invocation-start pairing window. A timeout is a terminal primary status even if underlying termination is unconfirmed; that uncertainty must remain recorded, and the stop-for-review rule still bars another invocation. If either arm was never invoked, do not run pair-level lookups; record candidate relevance as `unknown` with assessability reason `not_assessable`. A late primary response does not reset the budget or revise the primary result.

Within that budget, make at most one attempt per evaluation-only detail or audit lookup, with no retry. The fixed proposed ordering is: arms in their assigned invocation order; candidates in ascending rank within each arm; detail before audit for each candidate. Continue after a lookup failure only when time remains. This order gives the earlier arm and higher-ranked candidates priority if the deadline expires; report this ordering bias and do not interpret lower completion rates for later slots as irrelevance. Record every planned lookup, including one not started because the deadline arrived. Do not start any lookup at or after the monotonic deadline; responses completing after the deadline are supplemental only. Record monotonic and UTC start/end times, attempt count, HTTP status when received, sanitized error category, timeout and termination status, whether a response was late, returned candidate identity, content hash/revision, and linkage to the corresponding arm observation where available. Preserve response metadata such as Date, ETag, and request ID when returned. Do not save full response bodies or skill documents.

The 600-second cutoff is an operational bound, not a service guarantee. A response completed after it is marked late and retained only as supplemental data; it is excluded from primary reviewer packets. Missing, failed, late, unlinked, identity-mismatched, or revision/hash-mismatched evidence stays unknown or unverified as applicable and is never treated as irrelevant, negative relevance, or evidence of safety. If detail is unavailable by the cutoff, primary candidate relevance is `unknown`; missing, late, or mismatched audit evidence remains an unknown/unverified audit state, never a safety clearance. Where an observed arm hash/revision is absent, record linkage as `not_exposed` and do not claim revision-bound evidence.

Do not claim that cancellation terminates an in-flight request. Termination is not verified by this protocol. Record termination as `confirmed` only with positive evidence that the underlying request/process ended; `unconfirmed` when termination was requested or assessed but no confirmation was obtained (or activity remains observed); and `unknown` when no reliable termination signal was available or observed. A stopped harness wait alone supports neither `confirmed` nor successful cancellation. If termination is unconfirmed or unknown at timeout, stop before another invocation and require run review. Any later response is supplemental only. The shared budget still bounds primary evidence inclusion.

SkillScout's ordinary product workflow retains its configured retry behavior. The repository currently documents two retries after the initial attempt (up to three attempts for retryable failures); this value and actual attempts require runtime verification against the pinned revision. Record attempts when observable, otherwise use `unknown`. Evaluation-only post-arm detail/audit lookups use one attempt and no retry. The ordinary-search baseline also uses exactly one request with no retry. Disclose this intentional end-to-end asymmetry with results; do not attribute observed differences to ranking quality alone.

## 4. Statuses, decisions, and timing measure

Operational status is separate from policy decision, candidate evidence, and relevance. Apply these arm-level statuses:

| Arm status | Definition |
|---|---|
| not_run | The arm was scheduled but never invoked, for example after a run stop. |
| blocked | The arm was not invoked because a required precondition was absent; record a reason such as approved_context_unavailable or credential_unavailable. |
| failed | The arm was invoked but produced no valid arm-level response, for example a non-success HTTP result, transport error, 240-second harness timeout, unexpected harness failure, or malformed response. Record `harness_timeout`/`harness_failure` separately from underlying-request termination (`confirmed`, `unconfirmed`, or `unknown`). |
| partial | The arm produced a parseable response that is explicitly marked partial/truncated or is missing part of its arm-level result. Do not infer partial from an absent optional field. Missing audit evidence, a valid REVIEW decision, or incomplete candidate evidence in an otherwise valid structured response are evidence states, not operationally partial responses. Malformed top-level responses are failed. |
| complete | The arm produced a valid response. A valid empty search and valid NO_SKILL_NEEDED are complete arm responses. |

Apply these pair-level rules:

| Pair status | Definition |
|---|---|
| not_run | Neither arm was invoked because the run stopped before this pair began; include the stop reason. |
| blocked | Neither arm was invoked because a shared prerequisite blocked the pair. |
| failed | Both arms were invoked and neither produced a valid primary arm-level response. |
| complete | Both arms produced complete primary responses and the second invocation started at or before 300 seconds after the first. |
| partial | Any other combination, including only one arm invoked, an absent/late second start, a failed/blocked/not_run arm paired with another status, a partial arm response, or a second start after 300 seconds. Preserve all observed results and do not fabricate absent invocation timestamps. |

A parseable `partial` arm response is an observed primary result and makes the pair `partial`. `failed` applies only when both arms were invoked, both have failed status, and neither produced a valid arm-level response. A single-arm failure, a valid response paired with failure, and an unstarted paired arm are `partial`.

A valid SkillScout response has an explicit nullable decision field whose value is exactly one of NO_SKILL_NEEDED, USE, REVIEW, or AVOID. It is null if SkillScout was not invoked or no valid structured response supplied a decision. The ordinary-search arm always has decision=null. Store operational status and error category/message in separate fields. A catalog failure is never a no-skill outcome, and an empty valid search is not an HTTP/tool failure.

Candidate detail, audit, compatibility, scanner, and inspection completeness are candidate evidence fields, not arm decisions. A complete arm response can still contain REVIEW or incomplete candidate evidence. Do not imply that a clean heuristic scan proves safety.

Keep the metric name **Time to useful decision (TUD)**. For each arm, its approved operational endpoint starts at that arm's invocation-start event and ends when its primary response and required, identity-linked detail are available for human judgment across all occupied candidate slots. For a valid empty result or valid `NO_SKILL_NEEDED` with no candidates, the endpoint is the time the valid primary response arrives. If any required candidate evidence is still missing, failed, late, unlinked, mismatched, or otherwise not judgeable at the 600-second cutoff, TUD is censored/incomplete; do not report the cutoff as a successful decision time. A timeout or harness failure is a failed/incomplete observation, never a success.

Report these timing components separately, using monotonic durations and UTC event timestamps:

- **Arm response latency:** invocation start to the primary valid response or terminal operational status (including timeout/error). It is not evidence-retrieval time and does not imply success.
- **Evidence-retrieval duration:** elapsed time spent in the shared post-arm lookup phase, reported per arm and pair; identify lookup start, last primary completion, or deadline expiry.
- **Waiting attributable to the paired arm:** for the arm that reaches a terminal primary state first, the interval from its terminal state until the other invoked arm reaches its terminal primary state. It is zero/not applicable for an arm with no such wait.
- **Pair-level time to evidence-ready:** the first invocation-start event to the point both primary arm outputs and their required linked evidence are ready for reviewer judgment. It may include the inter-arm wait and the shared lookup phase. If either arm is not invoked, or required evidence is not ready by the cutoff, report it as not assessable or censored/incomplete; do not report a successful time.

Because lookups begin only after both invoked arms reach terminal primary states, TUD for the earlier-finishing arm and pair-level time-to-evidence-ready may include waiting imposed by the paired execution. Report that wait separately; do not interpret TUD as intrinsic, isolated model or service latency. These are approved policy definitions; this protocol does not establish that software enforces or records them.

### Slot accounting and interpretation

For each arm, the fixed-slot denominator is 126 planned top-three positions (14 eligible tasks × 3 repetitions × 3 positions). Before collection, report the exact denominators and count each position once: `relevant`, `irrelevant`, `unknown` (occupied candidate but evidence cannot support a relevance judgment), `unresolved_review` (no final label because review/adjudication is unresolved), `empty` (a valid completed response returned fewer than three candidates), `failed` (invoked but no valid primary response), `blocked`, or `not_run`. A parseable partial response's absent/truncated positions are `unknown`, not empty. An occupied, unresolved review is not silently converted to candidate relevance `unknown`.

Also report the evaluable-occupied-slot denominator: occupied candidate slots with a final `relevant` or `irrelevant` label. Show unknown and unresolved-review counts alongside it; never include either as irrelevant. Report decision outcomes per valid SkillScout response with failed/partial/not-run counts separately. Show denominators by arm and repetition. The 42 pairs are repeated observations clustered within 14 task units, not 42 independent tasks; interpret task-level outcomes as the independent units and report repetition and arm-order effects descriptively.

## 5. Blinded human relevance review

The proposed review uses two independent primary reviewers for each task-specific candidate revision. Reviewer availability has not been confirmed. Each blinded reviewer packet contains the exact task text, unchanged relevance criterion, approved context description, and candidate detail material, with system identity and task-level expected metadata removed. It must hide arm/system, expected decision, task-level expected label and category, score, rank, popularity, audit/safety findings, scanner findings, and reviewer crosswalk. Mask stable candidate IDs and source URLs wherever feasible. Candidate content or unavoidable metadata may identify a source; record what was exposed and each reviewer's source recognition, and report the exposure as a blinding limitation. Source recognition from content alone does not automatically invalidate a label.

If protected metadata is accidentally exposed, record the affected task/candidate and reviewer, the metadata exposed, and when exposure occurred relative to the label/adjudication. Preserve the original assessment and reason, mark blinding `compromised`, and do not present it as fully blinded. Obtain an independent replacement from an unexposed reviewer if available; otherwise the review resolution is `unresolved`. Apply the same rule to a third reviewer exposed before locking the independent assessment. No reviewer availability is assumed.

Generate an opaque candidate key for each task-specific candidate revision and shuffle review order with a recorded seed before review. The separate reviewer crosswalk has one row per occurrence, linking opaque key and task ID to pair/repetition, arm, rank, stable ID, source URL, and candidate content hash/revision. Store it separately with access restricted from reviewers until all blinded primary labels and any adjudication are locked. Do not include arm, rank, stable candidate ID, or source URL in reviewer-facing files where feasible; if a field cannot be masked without destroying reviewability, record it as unavoidable exposure.

Duplicate reuse is allowed only for the same task ID and same stable ID plus exact content hash/revision. That candidate revision may be reviewed once for that task and its label reused across arms/repetitions in that task. Review the same content revision independently for different tasks because the task and criteria differ. Different hashes are separate revisions. If no content hash is available, do not deduplicate on identity alone. Incomplete or untied content is unknown.

Each primary reviewer independently records candidate relevance `relevant`, `irrelevant`, or `unknown`, a short criterion-linked reason, source/system recognition, and blinding status. `Unknown` means the candidate evidence is insufficient, incomplete, unlinked, or mismatched to judge relevance. Record review resolution separately as `resolved` or `unresolved`; unresolved disagreement/adjudication or a compromised review without replacement is not a candidate relevance label and must not be recoded as `unknown`. If both valid blinded reviewers agree, preserve both records and use the agreed label. If they disagree, lock both initial reviews before the third reviewer sees the packet. The third reviewer first locks an independent blinded label/reason without seeing initial labels/reasons, then sees the two locked reviews and records separate adjudication without system, rank, or crosswalk. Preserve every assessment and rationale. If adjudication is unavailable, the final review resolution remains unresolved. If evidence itself is insufficient under Section 3, candidate relevance is `unknown` regardless of reviewer preference. Do not average labels or use SkillScout outputs as ground truth.

This reviewer procedure and third-reviewer decision rule are proposals requiring owner approval. No reviewer assignment or availability is asserted.

## 6. Future raw-results field specification

This section specifies future records only and does not establish recorder or validator implementation. A future run must preserve 42 pair records, including not_run, blocked, failed, partial, and complete outcomes; never omit an unexecuted planned pair.

The run manifest should include evaluation/addendum version, run ID, original dataset SHA-256, SkillScout source revision/package version, exact Python version, lockfile name/hash when a lockfile is available (otherwise explicit not_available), and installed dependency names/versions. Also include catalog base URL, configured candidate limit, effective search-pool size, baseline limit/order, MCP tool/transport, the approved 240-second arm invocation cap and its runtime-enforcement status, pairing and lookup deadline settings, LLM state (disabled), observed retry/attempt counts, context source and per-task reference/hash, catalog_mode (live, mocked, or offline), candidate_source (catalog or synthetic), and UTC run start/end. Record credential_configured as a boolean only; no values or environment dump. Values asserted by documentation but not observed at runtime remain marked `not_verified`.

Each JSONL pair record should include:
- Schema version, run ID, dataset hash, task ID, task_index, repetition, arm order, project-context hash, pair status/reason, both monotonic invocation starts, both UTC invocation timestamps when present, and pairing-window duration/result. Include arm response latency, pair wait attributable to the paired arm, per-arm and pair evidence-retrieval duration, per-arm TUD, and pair-level time-to-evidence-ready with completion/censoring status. An invocation that never started has no fabricated timestamp.
- For each arm: invocation start/end in monotonic time and UTC where observed; approved 240-second cap and timeout outcome; observable upstream request start/end in both time bases when possible; request/tool name; arm operational status; HTTP status if exposed; exit/error code and bounded sanitized error description; retry/attempt count; harness outcome; underlying-request termination (`confirmed`, `unconfirmed`, or `unknown`) and supporting evidence; late-response status. The primary baseline has exactly one request. Evaluation-only detail/audit lookup attempts are each exactly one, or zero with an explicit `not_started_after_deadline` status. SkillScout's internal attempts are recorded only if observable; otherwise use `unknown`.
- A nullable SkillScout decision enum (NO_SKILL_NEEDED, USE, REVIEW, AVOID) separate from status/error. Ordinary-search decision is null.
- Ordered candidate slots 1–3 with slot disposition, stable ID, source/slug, rank, detail status, detail request/response timestamps, attempt count, HTTP status when received, sanitized error, timeout/termination/late-response status, content hash/revision if supplied, identity_linkage, revision_linkage, audit state/revision/time and audit-to-content linkage, and available compatibility, scanner, and inspection-completeness evidence. Use explicit `unknown`, `not_provided_by_arm`, `not_exposed`, `not_started_after_deadline`, or null where appropriate. Record valid empty slots for a completed response with fewer than three candidates; missing slots in a partial response are unknown, not empty.
- Available response metadata such as Date, ETag, and request ID; note unfilled slots. Keep adjudication-only observations separate from arm outputs.
- No full skill contents, evidence-packet excerpts, credentials, full API response bodies, or unnecessary project source.

Blinded judgments are a separate JSONL file keyed by opaque candidate key and task ID, with reviewer pseudonym, candidate relevance label (`relevant`, `irrelevant`, or `unknown`), separate review-resolution status (`resolved` or `unresolved`), criterion-linked reason, source/system recognition, blinding status/deviation, and adjudication outcome. The crosswalk is a separate restricted file with one row per occurrence linking opaque key to pair/repetition, task, arm, rank, stable identity/source URL, and revision. Keep it inaccessible to reviewers; mask stable IDs and source URLs from packets where feasible. The third reviewer sees locked initial labels/reasons only after locking their own independent blinded assessment. Store summaries only as derivations of the raw records. Keep live, mocked, offline, and synthetic records distinguishable; a live-catalog run with synthetic project contexts must be labeled live catalog plus synthetic context, not a real-project study.

The recorder and validator may be implemented only after protocol-owner approval. Their schema and validation behavior require a separate review before any run records are collected.
